# Test Coverage Note (Week 3)

This note says what is tested, what is not, and why. The numbers come from a JaCoCo report generated by the test run, not from estimates.

## How to run the tests

```powershell
.\mvnw.cmd test
```

- Docker must be running. The integration tests start a throwaway PostgreSQL 16 container (Testcontainers) and run all Flyway migrations (V1 to V5) against it. They never touch the development database on port 5433.
- A full run takes about 2 to 3 minutes (most of it is Docker and Spring start-up). The unit tests alone take a few seconds:
  `.\mvnw.cmd test "-Dtest=MatchServiceTest,ApplicationServiceTest,ClaimedLevelTest,RegisterRequestTest"`
- The coverage report is written to `target/site/jacoco/index.html` (and `jacoco.csv`) by the same command.

## What is tested

**Authentication and security (integration)**
- Login with a seeded account returns a bearer token.
- Wrong password and unknown email return the same 401 `INVALID_CREDENTIALS` (no account enumeration).
- Blank fields, malformed JSON, a bad email, a short password and a password over 72 characters return 400.
- A duplicate email returns 409 `EMAIL_TAKEN`, including with different letter case and surrounding spaces.
- No token and a garbage token both return 401 in the standard error format.
- An EMPLOYEE calling manager-only actions gets 403, even for an id that does not exist (role is checked before existence).
- Unknown ids return 404, an unknown route returns 404, and a wrong HTTP method returns 405, all in the standard error format.

**Skill assessment workflow (integration)**
- A second pending claim for the same skill returns 409 `PENDING_CLAIM_EXISTS`.
- A claim at or below an already verified level returns 409 `ALREADY_VERIFIED`; a higher level is allowed.
- A manager cannot verify their own claim; an employee cannot verify at all; verifying twice returns 409.
- A rejection needs a comment (400 without one); a rejected claim can be made again.
- Another employee cannot read or withdraw my claim (403); the owner can withdraw a pending claim (then 404).
- An employee's list never contains other people's claims, even if another `employeeId` is sent.
- Invalid evidence (short summary, non-http URL) returns 400; an unknown skill returns 404.

**End-to-end journey (integration)**
One test walks the whole product: admin creates a skill, employee claims a level, manager creates, requires and publishes an opportunity, match is 0% before verification, manager verifies, match is 100%, employee applies, manager shortlists, employee withdraws.

**Business rules in isolation (unit)**
- Match calculation: only VERIFIED assessments count, the highest verified level per skill wins (in either order), a requirement is met at or above its minimum, the percentage rounds down (1 of 3 is 33, 2 of 3 is 66), and no requirements gives 0% without a division by zero.
- Match access: an employee cannot check another employee or an unpublished opportunity; a manager can.
- Application rules: you cannot apply to your own opportunity, to an unpublished one, after the closing date (but you can on the closing date itself), without a closing date, or twice.
- Application transitions: only SUBMITTED can be shortlisted; SUBMITTED or SHORTLISTED can be rejected or withdrawn; review order is role (403), existence (404), creator or admin (403); only the applicant can withdraw.
- The level order BEGINNER < INTERMEDIATE < ADVANCED < EXPERT is locked by a test, because the match uses `compareTo`.
- Request normalisation (trimmed name, trimmed and lower-cased email, password never altered, password never printed by `toString`).

## What is not tested, and why

These gaps are read from the package figures above. The exact uncovered methods are in `target/site/jacoco/index.html`.

| Gap | Evidence | Why it is not covered |
|-----|----------|-----------------------|
| Changing an employee's role or active status | employee.service 22.4%, employee.controller 37.7% | Lower risk than the verification workflow; not reached before the deadline. **Planned next if time allows.** |
| Opportunity update, delete, remove requirement and close paths | opportunity.controller 52%, opportunity.service 68.3% | The publish and requirement-add paths are covered through the journey; the rest were not prioritised. |
| Skill catalogue edge cases (for example duplicate skill name 409) | skill.service 44.8% | Creation is covered through the journey; the duplicate-name branch is not asserted. |
| Some error-handler branches | common 40.7% | Uncommon exceptions (for example unsupported media type) are not all triggered. |
| Tomcat's own HTML 400 for invalid percent-encoding in a URL | n/a | Raised before Spring sees the request, so our error format cannot apply. This is a documented known limitation (issue log), not a test gap. |
| Concurrency (two simultaneous applications or claims racing on a unique constraint) | n/a | The database constraints exist, but a race test needs a multi-threaded setup that was out of scope. |
| Performance and load | n/a | Not part of this suite; see `docs/performance-notes.md`. |
| Deployment and Docker Compose | n/a | The container build and `docker compose up` were verified by hand, not by an automated test. |
| Rate limiting, CORS and pagination | n/a | **Not yet implemented at the time of this run.** Tests for each will be added with the feature and this note updated. |

## Limits of this evidence

- Coverage shows which code ran, not that the assertions are strong enough. I checked assertions by reading failures during development, but there is no mutation testing.
- Instruction coverage is JaCoCo's default metric. It is not a measure of requirement coverage.
- Seeded demo data (V3 and V5) is used as a fixture by the auth tests. Tests that change state create their own users and data, so they do not depend on run order.
